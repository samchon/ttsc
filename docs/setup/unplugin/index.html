Unplugin (Bundlers)

When a bundler owns your build, the ttsc CLI never runs, and neither would your plugins. @ttsc/unplugin runs the same plugin pass from inside the bundler. It reads the same tsconfig.json and the same lint.config.ts, so there is no second configuration to drift out of date.

Adapters ship for Vite, Rollup, Rolldown, esbuild, webpack, Rspack, Next.js, Turbopack, Farm, and Bun. The import path is always @ttsc/unplugin/<bundler>. React Native and Expo bundle with Metro, which is not an unplugin target; that is a separate package with its own page, Metro (React Native).

Install

npm

npm install -D ttsc typescript @ttsc/unplugin

pnpm

pnpm add -D ttsc typescript @ttsc/unplugin

yarn

yarn add -D ttsc typescript @ttsc/unplugin

bun

bun add -d ttsc typescript @ttsc/unplugin

Then register the adapter that matches your bundler.

The package publishes matching ESM and CommonJS runtime and type branches. The default imports below type-check under both moduleResolution: "nodenext" and moduleResolution: "bundler"; CommonJS require() continues to expose each adapter as .default.

Keep the two versions together

@ttsc/unplugin declares ttsc as a peer dependency pinned to the minor it was published with. Both packages are released from one repository at one version, and the adapter compiles against ttsc’s exported compiler surface, so a 0.x minor is allowed to change what it imports. The pin is what turns that into an install error instead of a runtime failure in your bundler.

The consequence shows up with automated updates. A bot that opens one pull request per package will raise ttsc alone, and the install fails:

npm error While resolving: @ttsc/unplugin@0.25.0
npm error Found: ttsc@0.26.0

Nothing is wrong with either package. The two updates are one update, so tell the bot that.

# .github/dependabot.yml
version: 2
updates:
  - package-ecosystem: npm
    directory: /
    schedule:
      interval: weekly
    groups:
      ttsc:
        patterns:
          - "ttsc"
          - "@ttsc/*"

That raises one pull request carrying every ttsc package your project installs, which is the only shape that can pass. Renovate expresses the same thing as a packageRules entry with groupName over the same patterns.

Pin both to the same version in package.json for the same reason. If you upgrade by hand, upgrade them in one commit.

Vite

// vite.config.ts
import ttsc from "@ttsc/unplugin/vite";
import { defineConfig } from "vite";
 
export default defineConfig({
  plugins: [ttsc()],
});

A query that makes the host generate a module around a source file is left to the host: ?raw, ?url, ?inline, ?no-inline, ?worker, and ?sharedworker, on Vite and on webpack or Rspack rules that use the same names. import text from "./schema.ts?raw" therefore yields the file’s own text, and importing the file both ways compiles the project once. Every other query still denotes the file’s program and is transformed, including cache busting such as ?t=, the ?worker_file entry, and route chunks such as React Router’s ?route-chunk=.

ttsc compiles each file from disk. A module that reaches it with different text, because a plugin ordered before ttsc rewrote it or the file changed after the host read it, is served from the file’s compile. ttsc reports that once per file and never recompiles the project for it, so a rewrite made before ttsc runs is visible rather than silently lost. Order such plugins after ttsc, which runs with enforce: "pre".

Rollup

// rollup.config.ts
import ttsc from "@ttsc/unplugin/rollup";
 
export default {
  input: "src/index.ts",
  output: { dir: "dist", format: "esm" },
  plugins: [ttsc()],
};

One caveat worth knowing before it costs you an afternoon: the adapter emits transformed TypeScript, not JavaScript, and plain Rollup does not compile TypeScript itself. Add an esbuild- or swc-based plugin after ttsc(), or the build fails parsing type syntax. Bundlers that strip types on their own (Vite, Rolldown, esbuild, Bun) need no such step.

Rolldown

// rolldown.config.ts
import ttsc from "@ttsc/unplugin/rolldown";
 
export default {
  input: "src/index.ts",
  output: { dir: "dist", format: "esm" },
  plugins: [ttsc()],
};

Same shape as Rollup, but Rolldown ships its own TypeScript transform, so the downstream compile step Rollup needs does not apply here.

esbuild

import { build } from "esbuild";
import ttsc from "@ttsc/unplugin/esbuild";
 
await build({
  entryPoints: ["src/index.ts"],
  outdir: "dist",
  bundle: true,
  plugins: [ttsc()],
});

webpack

// webpack.config.mjs
import ttsc from "@ttsc/unplugin/webpack";
 
export default {
  entry: "./src/index.ts",
  plugins: [ttsc()],
};

Rspack

import ttsc from "@ttsc/unplugin/rspack";
 
export default { entry: "./src/index.ts", plugins: [ttsc()] };

Next.js

// next.config.mjs
import withTtsc from "@ttsc/unplugin/next";
 
export default withTtsc({
  /* your Next config */
});

withTtsc covers both of Next.js’s bundlers: it injects the webpack plugin and wires the Turbopack loader rules, with the options you pass reaching both. Your own webpack hook and turbopack block are preserved, and a rule you already wired for this loader by hand is left alone rather than registered twice.

That last part is decided by exact spelling. withTtsc declines to add its own rule when your glob is one it has measured against a real Turbopack build as naming every file with the extension: *.ext, **/*.ext, and {**/,}*.ext for each of ts, tsx, mts, and cts; plus the *.{...}, {*.ext,...}, **/*.{...}, **/{*.ext,...}, and **/**/*.{...} forms for every canonical combination of two or more extensions chosen from that same list. Any other spelling keeps your rule and gains ours beside it, so a module may be transformed twice rather than not at all. The list is exact on purpose: treating an unmeasured glob as project-wide once left every module in a project with no ttsc rule at all, and a build that transforms twice is recoverable in a way a build that never transforms is not.

Turbopack

Turbopack has no JS plugin API, but it runs webpack loaders through turbopack.rules, and a ttsc transform is loader-shaped: TypeScript source in, transformed source out. In a Next.js project withTtsc wires this for you; do it by hand when Turbopack runs outside Next, or when you want the rules under your own control. Reference the standalone loader by module name (do not call it):

// next.config.mjs
export default {
  turbopack: {
    rules: {
      "*.ts": { loaders: ["@ttsc/unplugin/turbopack"] },
      "*.tsx": { loaders: ["@ttsc/unplugin/turbopack"] },
      "*.mts": { loaders: ["@ttsc/unplugin/turbopack"] },
      "*.cts": { loaders: ["@ttsc/unplugin/turbopack"] },
    },
  },
};

Options go through the rule’s options object: { loader: "@ttsc/unplugin/turbopack", options: { project: "tsconfig.build.json" } }. The loader applies the same filter the unplugin adapters apply, so a rule glob wider than the four above still passes declaration files, node_modules paths, non-TypeScript sources, and virtual ids through untouched.

Turbopack runs the loader in a pool of worker processes, and each one keeps its own cache. Under withTtsc they share each compile: the wrapper opens a session in the process that reads the Next config, and the workers inherit it. The first worker to need a project state compiles it while the others wait, and they adopt it only after proving it against their own filesystem, including every file outside the project that a plugin reported reading. A cold next build and each edit therefore compile the project once, not once per worker. The session’s store lives under the system temporary directory, never in the project, and is removed when the process exits. A crashed worker never blocks the others, which take over its compile. With hand-written turbopack.rules and no withTtsc, each worker compiles for itself.

Turbopack fails a module whose dependency lies outside its project filesystem root. That root is the one the configuration names in turbopack.root or outputFileTracingRoot, or, when it names none, one Next detects from the lock files. So the loader hands Turbopack only the compiler inputs inside the deepest root the configuration names, and inside the project directory when it names none, which every Turbopack root contains. A development session’s bridge observes the rest, and a module that read an input outside that directory also depends on a marker file created once per process, so a result Turbopack persisted in an earlier process is never reused for it. In a monorepo, where types often come from workspace packages beside the app, set turbopack.root to the workspace so Turbopack can track and cache those inputs itself. withTtsc hands the loader the roots the configuration names. A rule wired by hand names them in its options: { turbopackRoots: ["/path/to/workspace"] }. When the configuration names no root and a module reads an input beyond the project directory, the loader says so once per project, as a Node process warning with code TTSC_TURBOPACK_UNTRACKED_INPUTS.

Farm

import ttsc from "@ttsc/unplugin/farm";
import { defineConfig } from "@farmfe/core";
 
export default defineConfig({ plugins: [ttsc()] });

Bun

import ttsc from "@ttsc/unplugin/bun";
 
await Bun.build({
  entrypoints: ["./src/index.ts"],
  outdir: "./dist",
  plugins: [ttsc()],
});

Under Bun.build, the adapter yields to the next loader for declarations, node_modules, source that ttsc leaves unchanged, and entries supplied through Bun.build({ files }). In-memory entries remain with Bun because ttsc transforms filesystem-backed project inputs. Bun’s runtime onLoad contract does not accept an undefined result, so Bun.plugin() returns excluded and unchanged filesystem files with their original source and does not chain another overlapping runtime loader. NUL-prefixed virtual ids remain outside the adapter’s filesystem filter. Each Bun.build opens a delivery pass through onStart, then onEnd disposes the completed project generation and its filesystem trackers.

For the Bun runtime, bun run, bun test, or any bun <entry>.ts with no bundling step, register the transform on Bun’s module loader with @ttsc/unplugin/bun-register. Add a bunfig.toml preload once:

preload = ["@ttsc/unplugin/bun-register"]

Now every bun run / bun test applies your ttsc plugins as files are imported, with plugin options from the nearest tsconfig.json. To pass options, or register imperatively, call it from your own preload module instead:

// bun-preload.ts   (bunfig.toml: preload = ["./bun-preload.ts"])
import { register } from "@ttsc/unplugin/bun-register";
 
register({ project: "tsconfig.build.json" });

Importing @ttsc/unplugin/bun-register registers exactly one runtime loader, shared by CommonJS and ESM loads in the same Bun process. Calls made before the first transformable TypeScript load use last-call-wins and capture their options by value, so an immediate explicit call can replace the preload defaults. Entering the first such load locks the options synchronously for the immutable module-loading session. A later call with the same structural value is idempotent, while a different value throws. Restart the Bun process after changing registration options, source, tsconfig, or plugin inputs.

Options

Most projects need none: the adapter finds tsconfig.json on its own, and your plugins and lint.config.ts apply unchanged.

The adapter selects each file’s project the way TypeScript’s editor tooling does. It starts from the nearest tsconfig.json and keeps it when that config’s files and include admit the file. A solution config admits nothing itself: it declares "files": [] and lists the real projects under references, as the create-vite react-ts template and tsc -b layouts do. For such a config, the adapter searches the referenced projects depth-first, in declaration order, and compiles the file with the first one that admits it. src/App.tsx therefore compiles under tsconfig.app.json, and vite.config.ts under tsconfig.node.json. Every config the search read on the way is watched as well: the solution, each project searched before the one selected, and a referenced config that does not exist yet. Editing the solution’s references, widening an earlier project’s include, or creating that config therefore re-routes the file. A reference is resolved as TypeScript resolves it, so "./tsconfig.app.json" names that file and "./packages/lib" names the tsconfig.json inside it. A file no project admits is left untransformed, the notice names every project that was searched, and those projects stay watched, so the file is compiled as soon as one admits it.

Three options layer on top:

  • project points at a non-default config file, resolved from process.cwd():
ttsc({
  project: "tsconfig.build.json",
});
  • compilerOptions overrides compiler settings for this build without another config file.
  • plugins replaces the project’s plugin list entirely; plugins: false disables them.

Path aliases

Under Vite, the adapter reads the resolved resolve.alias and layers it onto the generated config, so an alias declared only in vite.config.ts still resolves during the compile. No other host’s alias configuration is read: under Rollup, Rolldown, webpack, Rspack, esbuild, Farm, Turbopack and Bun, the compile resolves through the tsconfig’s own paths alone. Declare an alias in paths when a module has to resolve for the compiler as well as for the bundler, which is what those hosts need anyway for tsc to type-check the same imports.

Not every Vite alias form can be forwarded, because a tsconfig paths map cannot express all of them:

resolve.alias formForwarded
a string find whose replacement is an absolute pathyes
a replacement with a leading / outside the root, such as { "@": "/src" }yes, as the Vite root’s src first and the absolute /src second, the order Vite tries them
a relative replacement, such as "./src"no: Vite resolves it against each importing module, which paths cannot express
a bare replacement, such as "lodash-es"no: Vite resolves it as a package, which paths cannot express
array form with a RegExp find, such as { find: /^~/ }no: paths has no regular-expression form
a string find containing *no: a paths key already reads * as its own wildcard

In every unforwarded case the compile resolves that specifier through the tsconfig’s paths alone, and a forwarded alias never replaces a tsconfig mapping with a meaning Vite does not give it, so declare it there if ttsc must resolve through it. A prefix RegExp such as /^~/ is written as a "~/*" entry. Reducing simple prefix patterns automatically is deliberately not attempted: distinguishing /^~/ from /^@app/, which also matches @apple, needs enough of a regular-expression engine that a wrong reduction becomes likely, and a mistranslated alias resolves imports to the wrong file without saying so.

A find containing *, and a relative or bare replacement, is also reported once on stderr, naming the alias and the reason. A RegExp find is not, and the asymmetry is deliberate: Vite merges two RegExp aliases of its own into every resolved config, for @vite/env and @vite/client, so a report on that form would fire in every build of every project and name aliases you never wrote.

Source maps

Every transformed module comes with a source map back to the text you wrote, so stack traces, breakpoints, the error overlay, and a production build’s maps point at your own lines. That holds even though the compiler reprints the file and a plugin such as @ttsc/banner or typia inserts code above it. Vite, Rollup, Rolldown, Farm, and Turbopack receive the map with the transformed code. webpack and Rspack receive it from a loader the adapter places right after its own, because unplugin’s loader hands a transform’s map on only to a module that already carried one, and so to none that ttsc transforms first. esbuild and Bun take it as an inline sourceMappingURL in the loaded contents. Under Metro, whose transformer returns an AST rather than a map, @ttsc/metro moves the upstream transformer’s AST locations back to your lines, and Metro builds its map from them.

A module gets a map only when the compile read exactly the text the bundler delivered. When an earlier plugin already changed that text, the module is still transformed, but without a map, because a map of the file on disk would point at the wrong lines. An executable plugin host that writes no maps keeps working the same way.

Cache and watch invalidation

The compiler replays each resident module, type-reference, and triple-slash path resolution through the pinned TypeScript-Go resolver and reports the exact filesystem inputs it consulted. @ttsc/unplugin registers importer-owned inputs from a transformed file’s reference closure, plus universal automatic type-root discovery inputs, so changing a package manifest, failed probe, selected lexical link, unresolved search, or @types directory membership invalidates the transform even when neither an importer nor its tsconfig changed.

Entries in compilerOptions.types, including package subpaths such as tsdown/client and relative type paths, retain the original project’s resolution context when the adapter creates a temporary config. Mixed-case project paths and linked packages are supported on Windows and case-insensitive macOS filesystems. A change to an automatic type’s resolution affects the whole project, so its failure can report every source file.

A dev server configured without a watcher (server.watch: null, which is how vitest --run and other one-shot consumers configure Vite) receives no watch registration at all. Nothing can deliver a change event there, while Vite’s import analysis resolves every registered path like a real import of the transformed module, once per module. No private watcher or predicate poll runs in that watcherless session.

Under a watching Vite dev server, compiler dependencies are kept in a separate filesystem watch graph. They never enter Vite’s runtime import graph: a type-only server module, declaration file, or plugin configuration asset is not a runtime import. One recursive project observer plus at most 16 external scopes serves every dependent module, including files in node_modules, which Vite’s own watcher ignores. Compiler graph size therefore does not determine the native descriptor or timer count on macOS and Windows. On Linux the watch count follows the distinct directories leading to those inputs, never the files below them. A file event updates the dependent modules in each environment through Vite’s own reloadModule, the propagation an edit to those modules would trigger. HMR boundaries, SSR, and the decision to reload the page are Vite’s, so an accepting component keeps its state when a type it validates against changes. A server with hmr: false, or a Vite without the API, invalidates the modules in every graph and requests a full reload instead. Missing paths and directory predicates use the recursive observer for their nearest available scope. Inputs outside the scope ceiling or behind a failed observer, hardlink alias, or linked topology share one fallback scheduler that checks at most 64 entries and 64 links per tick. A successful retransform replaces that module’s subscriptions. Failed transforms retain known dependency paths so restoring a deleted input can announce recovery. Server shutdown awaits watcher cleanup. Production builds and other bundlers use their native dependency-registration contracts.

The esbuild adapter uses native file and directory subscriptions, so adding or removing an automatic type package also rebuilds its consumers. Failed loads retain recovery dependencies, including when the first build fails. Unchanged rebuilds reuse the shared compiler generation, and the final build or context disposal releases it.

Farm opens a delivery pass for each incremental update as well as its initial compilation. Repairing a compiler input retries a failed generation in the same update session; unchanged successful updates reuse their generation.

The linked native transform host retains the loaded program’s dependency graph when compilation fails. Missing external declarations remain observable even when the first build fails and its diagnostic names only the importer. Compiler errors and plugin failures return structured diagnostics and recovery inputs without publishing partially transformed source.

Bundlers invalidate a module only when its registered inputs change, and they erase type-only imports from their module graphs, but a type-driven transform’s output depends on the files where the consulted types are declared. @ttsc/unplugin closes that gap by registering, per transformed file, the compiler-reported reference closure (type-only edges included), the files contributing to the global scope, and the tsconfig extends chain as watch files. The JavaScript host also registers the descriptor’s loaded CommonJS graph, every package manifest inspected by auto-discovery, and plugin-declared hostInputs; first-party plugins use that declaration for implicit config discovery and evaluated config dependencies. Arbitrary project assets do not become universal inputs. Webpack filesystem caches (what Next.js persists under .next/cache), watch-mode rebuilds, and Turbopack fileDependencies all consume that registration, so editing a type another file’s generated code depends on rebuilds the consumer without deleting any cache.

Each input reaches the host through the channel that observes what the compiler recorded about it. A file the compiler read is a file dependency. A path it found missing uses the channel that reports a creation: addMissingDependency on webpack and Rspack, and the file channel elsewhere. esbuild keeps one watch state per path, so there a path probed as a directory goes to watchDirs, one probed as a file to watchFiles, and one that either could replace is observed through its parent’s watchDirs listing. A directory whose entries it listed uses a directory channel, watchDirs on esbuild and addContextDependency for a one-shot webpack, Rspack, or Turbopack build. A directory it only checked exists is not registered at all, because each path it probed below that directory is registered in its own right. A tool writing into node_modules therefore no longer starts a rebuild.

The program’s root files are not something the compiler reports, since the adapter’s own project walk decides them, so a watching session also registers them as one input for the project root. The build bridge and the Vite dev server’s watcher observe every directory the walk enters, judge each event by the walk’s membership rule, and re-walk the project when one counts. A new root file then rebuilds every module of the project in a watching build, and invalidates them in the dev server without an HMR update. esbuild takes the walk’s directories as watchDirs. A one-shot webpack, Rspack, or Turbopack build takes nothing, because its directory channel is recursive: a persistent cache that a later build replays cannot hear a new root file, and must be cleared after adding a declaration that changes other modules’ generated code.

Some host channels cannot observe a predicate precisely, so a watching session hands those inputs to an adapter-owned bridge instead:

  • Rolldown and Farm report neither a created path nor a new directory entry, so missing paths and listings go to the bridge.
  • webpack, Rspack, and Turbopack watch a directory recursively. The compiler lists the project root, so a context dependency there reacted to every write, the build’s own output included, and next dev re-ran the loader hundreds of times per change. Listings go to the bridge.
  • Rollup opens one watcher per registered path, and a recursive one for a directory, so every input goes to the bridge.

A path the host’s own watcher skips goes to the bridge as well. Rspack skips node_modules and .git unless watchOptions.ignored says otherwise, and the webpack configuration Next.js builds skips node_modules, .git, and .next. Without the bridge, a declaration package installed during a watching session would never rebuild. The input keeps its host channel, so the host’s persistent cache still records it. The adapter does not evaluate a glob in watchOptions.ignored, so with one configured every input goes to the bridge as well, which can cost a second rebuild but never misses one.

Under next dev, every input goes to the bridge as well. Turbopack reads a dependency’s state only when it processes the loader’s result, and takes that state as its baseline, so a change saved between the compile reading a file and that moment was part of the baseline and never re-ran the module. The bridge proves at registration that nothing changed since the compile read each input, and observes each one from then on. When a module turns stale, the bridge rewrites its sentinel after a short delay and again at intervals four times longer each time, until the module runs again. However late Turbopack takes its baseline, a later rewrite lands after it, and a module Turbopack never asks for again costs about eight rewrites in its first hour and fewer every hour after. The module’s next run stops the rewrites.

The bridge is the bounded observer the Vite dev server uses, with the same precise re-check per event. It signals the host by rewriting one sentinel file per module, and the host watches only that file. The sentinels live below the system temp directory, except Turbopack’s: Turbopack fails a module whose dependency leaves its project filesystem root, so its loader keeps them in the project’s node_modules/.cache/ttsc, beside ttsc’s own cache. A bridge removes its sentinels when it closes, and one that starts removes those of a process that died without doing so. It opens only in a watching session, never for a one-shot build, and closes with the host’s watcher.

This works for every adapter automatically when the transform host emits the envelope’s graph section. The built-in host and linked plugins always do; executable sidecar plugins adopt through the driver SDK. Plugins whose output additionally depends on non-file inputs declare those files volatile, which excludes them from caching entirely.

A plugin that knows exactly which declarations it consulted can go the other way and declare its reported list complete for a file. The adapter then registers only that list plus the tsconfig chain for it, so a change to a file the transform never read stops re-running the loader. Nothing is required of you: the field is per file and opt-in per plugin, and a plugin that never declares it keeps the sound default above.

One whole-project compile already contains every module’s output, so the adapter compiles once and serves every module from that result. What follows is how it decides that the result still describes the project on disk.

What the snapshot covers

The transform cache snapshots every regular file reached by the non-following project walk, plus the graph-reported inputs outside that walk: node_modules declarations, monorepo sibling sources, files reached through symlinks or Windows junctions, and out-of-root extends ancestry.

The project is snapshotted before and after compilation, and every graph member carries the compiler filesystem’s content and physical-identity proof. Only a complete generation that still matches both may authorize narrow reuse. That also rejects an A to B to A change whose restored post-compile bytes would otherwise hide the transient state the compiler actually read.

Delivery passes

A host with a build boundary opens a delivery pass there and keeps the generation it already holds. A native compile opens one temporary recursive observer around the capture so a transient change cannot hide between equal before and after snapshots, then closes it before delivering any module. No build-scoped observer remains in the cache. The pass’s first delivery proves the whole generation against the current filesystem once, and after that each module’s first delivery in the pass is settled by the supplied source alone. An incomplete generation never takes that shortcut.

A pass boundary states that each module is requested at most once inside it, which is a fact about deliveries rather than about whether the compiled program is still correct. buildStart repeats per rebuild under webpack, Rspack, Rollup, Rolldown, esbuild and vite build --watch, so discarding the generation there recompiled the whole project on every edit. The boundary now opens a pass and the recorded snapshot decides whether the generation survives it.

Long-lived hosts without a boundary (Metro workers, the Turbopack loader, and a watching Vite development server, whose initial buildStart spans later HMR edits) apply the file-specific validation on every generation hit. Those deliveries validate that file’s reference closure, globals, configs, importer resolution inputs, universal automatic-type inputs, plugin dependencies, and exact host inputs, so sibling modules share one proof of the closure and the universal inputs rather than repeating it per module. On an unchanged proven generation, a Vite delivery reads no source bytes and performs two metadata checks: one of the adapter’s own clock probe, which lets recorded signatures stand for content, and one of the project root, which confirms its watchers still observe the directory they opened on. Deriving a sibling’s watch inputs performs no filesystem probe, regardless of graph edge count.

Program membership

Root-file discovery follows TypeScript-Go’s own selection. include and files merge across extends as TypeScript-Go merges them, including inherited paths and ${configDir} substitutions, and a config that declares neither includes every file below its own directory, exactly as TypeScript-Go does. A files-only project has no implicit include. Wildcards never enter node_modules or other package folders, or any directory whose name starts with a dot, so the output tools write to node_modules/.vite-temp, .cache, or .turbo is never a program input. A spec that names such a directory literally, such as .react-router/types/**/*, still reaches it. With resolveJsonModule, a JSON file enters the program only through a files entry or an include spec ending in .json, so coverage reports written under coverage/.tmp do not count. A wildcard also leaves out .min.js files unless it spells .min. itself. The adapter skips unrelated directory trees and their rename events, so test scratch directories outside the configured search cannot invalidate a transform generation. Matching new files and directories still invalidate it, including when the project is opened through a junction or a Windows short path. Case-insensitive matching includes Unicode case variants. Imports and plugin dependencies outside that search remain tracked as external inputs; include is not an import restriction.

Membership comes from the resolved configuration rather than from a list of directory names. allowJs and resolveJsonModule decide which extensions can enter the program, and only a config that cannot be read falls back to excluding .git, node_modules and .ttsc by name. The project walk, its path predicate, and the live membership watcher all apply that one rule. When no top-level exclude is declared, TypeScript uses outDir and declarationDir as implicit directory exclusions; an explicit exclude, including an empty array, replaces those defaults with its own entries. Adapter compilerOptions replace or clear inherited outDir and declarationDir values before membership is derived, and ${configDir} paths follow TypeScript’s config-relative substitution.

A directory outside root-file discovery or selected by the effective exclusion rule is not walked at all. Within the configured search the digest records the entries the walk considers rather than each directory’s own stamp, and a directory takes part only while its subtree can hold a program input. An output directory no effective exclusion names therefore costs nothing, however its filenames churn, as long as the project cannot admit what it holds; under allowJs an emitted .js beside the sources is a program input like any other, so such a project should name that directory in exclude. Emptying and recreating a directory the effective exclusions name, which emptyOutDir and output.clean do on every build, is not a change either, on a host with a build boundary or without one. A directory that takes no part is still walked and still watched, which is what makes the first source appearing in it a change the generation sees. The walk hashes only files that could enter the program, and validation compares only the generation’s declared inputs, so a tree of emitted files costs no reads.

Generation-scoped directory notifications detect new, removed, or renamed project inputs without repeating a directory-stat pass per module. Windows isolates those notifications, the Vite dev server’s compiler-input observers included, so deletion of a watched temporary tree cannot crash the host. Linux has no native recursive notification, so there each observer watches only the directories it needs, with one watch per directory shared by every observer in the process. It watches the directories the project walk enters, the directories leading to each tracked input, and each new directory among them as it appears. No observer walks node_modules or watches a single file, so capture time and the inotify watch count do not grow with installed packages. A watch the system refuses, the per-user inotify limit included, falls back to snapshot validation. A reported membership event is evidence of a change and replaces the generation.

Those Linux watches do not go through fs.watch. An inotify instance queues at most fs.inotify.max_queued_events events, 16384 by default, and once the queue is full the kernel drops the rest and queues one overflow notice, which libuv discards, so a burst such as an install or a large checkout could lose events without a trace. Every Linux watch of the adapter therefore lives in a helper process, the hidden __watch command of ttsc’s platform binary, the one ttsc itself resolves. It owns one inotify instance, reports an overflow to every watch as an event without a name, and answers a delivery’s barrier only after reading its queue empty, so an edit made before a delivery has always reached the watchers when the delivery reads them. A watch goes live when the helper confirms it, and a directory is read only after that. When the helper cannot start, or exits, no Linux watch is trusted: every generation validates against its recorded state, and the Vite dev server polls.

Notifications about inputs outside the project walk count only the events that can change what the compiler observed about each input.

  • A declaration the compiler read counts a change to its own content.
  • A directory the resolver only probed for existence, such as node_modules, counts only its own rename. Writes below it, like vitest caching results, record nothing.
  • A directory the compiler listed, such as an @types root, counts renames of its direct children.
  • A missing path counts anything that appears at or below its first missing component.
  • An absent resolution candidate that exists as a directory counts anything below it, because only replacing that directory can turn it into the file the compiler looked for, and a recursive delete reports the directory’s contents before the directory itself.
  • Every input also counts a rename of any of its ancestors, because moving or replacing a directory moves its contents without an event on each of them.
  • An event the backend cannot attribute to a name counts for every input below the watched directory, whatever its type. On Windows that is how a watch reports that its buffer overflowed and events were lost, and on Linux how the watch helper reports an overflowed inotify queue.

Every platform applies these rules through the same decision, so the isolated notification broker, which hosts the Windows and macOS watches, and the Linux watch helper agree. On Linux and macOS, a watch keeps following the directory it opened on after that directory is replaced. Every delivery therefore re-checks each watched directory’s identity and stops trusting notifications from one that changed; the Vite dev server’s external observers are re-checked by the same bounded poll. The Vite dev server never observes the project root’s ancestors: TypeScript-Go probes node_modules in each of them, and an input whose nearest existing directory is such an ancestor is polled instead, so no watch ever covers a home or AppData directory.

Proving an input unchanged

Every input a generation has already proven carries the nanosecond metadata signature captured around the read that proved it, so a later delivery that finds the signature unchanged reuses that proof instead of re-reading the bytes. Any signature change falls back to the full content comparison.

A signature is recorded only for a read nothing raced, only for an input whose recorded state came from bytes that were read, since the metadata of a path nothing could read holds still while the bytes behind it appear, and only once the observed filesystem’s own clock has provably left the tick that minted the input’s modification stamp.

A filesystem stamps writes once per clock tick, so a same-length rewrite landing inside the recorded stamp’s tick would leave the signature unchanged. Until some stamp the same filesystem minted later separates that tick, the content comparison keeps running, and the signature is re-earned the moment it can be.

The reference instant comes from the filesystem itself, never from the process clock or a timestamp merely observed on another input. The adapter retains a temporary probe outside the project and rewrites it immediately before every validation that may reuse a content signature, the way git separates racily-clean index entries with the index file’s own timestamp. The old reference is discarded before the write, so a future timestamp assigned by an extraction or copy cannot forge progress and a filesystem clock rollback cannot leave historical proof behind.

The probe counts only for inputs on its reporting device. Both sides of that comparison have the same granularity and clock origin, so a constant offset from the process clock changes nothing. If the probe cannot be refreshed or its volume differs from an input’s volume, the adapter keeps the content comparison. It never guesses at clock offsets and never writes a probe into the user’s project.

Inputs that are not there

An absent resolution candidate is the one input a metadata signature cannot stand for, since a path that is not there has no metadata to compare. The generation registers those names with a watcher of their own, along with the directory components of the spelling that lead to them, down to the project’s own root, and a delivery reads the notification instead of re-probing each candidate.

That makes the notification the sole positive evidence for this one input class, which is why the registration reaches past the candidate itself: a watcher opened on a path that traverses a link follows it, so retargeting the link would otherwise move the answer without disturbing what is watched, and a package link inside node_modules is exactly that. It stops at the project root, and a candidate whose spelling leaves the project subtree before reaching it is not claimed at all, because above that line the components are the machine’s own layout rather than the project’s.

It listens for renames alone, since every event that can change a candidate’s answer is one: the file appearing, a component being created, replaced or retargeted. The directories carrying them have their attributes moved by anything written below.

A candidate whose watch could not be opened, whose watcher has since failed, or that belongs to a set spanning more directories than the generation will watch, is probed exactly as before. Reaching the external-scope ceiling falls back to recorded snapshots instead of opening a broad system-directory observer. A host that rejects a watcher also falls back to snapshot validation, which preserves correctness without letting descriptor count grow with the compiler graph.

What none of that covers is a filesystem that accepts a watch and then reports nothing, which some network mounts do. That is the same assumption the project-membership proof beside it already rests on, though a wider one here, since the project walk skips node_modules and a candidate under it was never covered by that proof. A project on such a mount should be treated as one where notifications do not work rather than one where they merely have not fired.

Declare that the way your tools already expect, and ttsc honors the same declaration. A generation then keeps no watcher, and every delivery validates against the recorded snapshot. Each declaration is read exactly as the tool that owns it reads it:

  • Vite’s server.watch.usePolling. With it, the dev server’s compiler-input watcher opens no native observer either, and every compiler input goes to the bounded poll, which checks at most 64 inputs every 500 ms.
  • CHOKIDAR_USEPOLLING, which overrides usePolling inside Vite: false and 0 turn polling off, and any other non-empty value turns it on.
  • WATCHPACK_POLLING, which webpack and Next.js read: a number polls unless it is 0, and any other value polls unless it is empty or false.

Without a declaration, native observers keep their bounded cost, and an unchanged generation still costs those two metadata checks per delivery.

The barrier that lets a synchronous edit reach those watchers before a delivery reads their verdict is the watcher’s own acknowledgement rather than a fixed wait. An in-process watcher answers on the next turn of the loop its callbacks are queued on, and the broker answers by an ordered round-trip, so a delivery waits for the crossing instead of guessing at it. A barrier the broker does not answer within a second proves nothing, since an event may still be in flight: the watchers’ silence is not trusted until one delivery has proven the recorded state by reading it.

macOS needs the broker for a second reason. libuv serves every directory watch of one event loop through a single FSEventStream, and re-creates it whenever any watch in that loop opens or closes. The old stream stops without delivering what it still held, and the new one starts from that moment, so every watch in the loop misses whatever happened in between. libuv also discards the notice FSEvents gives when it dropped events, whether the kernel or the client fell behind, so such a loss went unnoticed too. The broker therefore watches through the fsevents binding, an optional dependency that package managers install on macOS: each watch is its own stream, started before the registration is reported ready, and opening or closing one disturbs no other. When a stream reports dropped events, a changed root, or a mount below it, the broker warns every registration of that stream: a generation stops trusting its watchers’ silence until one delivery has proven its recorded state by reading it, and a Vite dev server scope re-checks every input it covers. Installed without optional dependencies, the broker has no watch it can trust on macOS, so every generation validates against its recorded state and the Vite dev server polls; the adapter says so once, as a Node process warning with code TTSC_FSEVENTS_MISSING.

Narrowing by declared completeness

dependenciesComplete narrows file inputs by the same contract as watch registration, and a project reaches it without a type-driven plugin: ttsc’s own transform lanes print syntactically, so the host declares every file complete when no plugin can contribute to it, and the first-party @ttsc/banner and @ttsc/strip declare their own contribution the same way. Such a delivery validates the universal inputs and the file itself instead of its reference closure.

A narrowed file’s diagnostics narrow with it: an edit to a file the declaration dropped no longer re-runs the compile, so a type error introduced there surfaces at the next compile the build runs for another reason rather than at the edit. Run the compiler’s own check beside the bundler when you want it at the edit.

Envelopes without a graph, and generations whose watchers could not be opened or have since failed, retain complete-snapshot validation. Losing a notification is the absence of a membership proof rather than evidence of a change, so such a generation keeps validating against its own recorded state: the directory snapshot, the input hashes, and the universal descriptor inputs whose every rejection is evidence of a change rather than an inability to prove one.

Failures and lifecycles

For a caching host, an unstable or incomplete attempt is never published: all waiters share one bounded stabilization retry inside the same generation. Whether an attempt is stable is decided by the evidence that spans the compile: the before and after project snapshots, the project watcher opened before the compile, the compiler’s own input proofs, and a stable configuration. The watchers for host inputs and absent candidates open after the compile, so they cannot see what it read. Their events never fail an attempt. Another tool writing under node_modules while a transform is captured, such as vitest next to a dev server, leaves the attempt valid. An event they record instead makes the next delivery prove that input again. A stable retry alone resolves and is reused, while a second unprovable attempt rejects the shared generation with bounded path-and-proof witnesses. That terminal verdict stays cached while its project, external, and host-input fingerprints remain unchanged, and the compile count is independent of module count. The confirmation runs once per event-loop turn and is shared by every delivery of that turn. Any file or input whose metadata signature is unchanged is proven without reading it, so a request wave against an error overlay costs metadata calls, not a re-read of the project per module. A write is seen from the next turn on, which is when a host delivers the module its watcher reported.

On POSIX, adapter process launches use the direct native spawn path. If Darwin rejects that launch with EBADF because unrelated open descriptors pushed a capture descriptor above the platform’s spawn limit, ttsc retries through a shell-free broker that inherits only standard descriptors. The retry preserves arguments, working directory, environment, timeout, exit status, signal, and complete output. The normal path pays no broker cost.

An input change or an explicit cache lifecycle reset permits a new generation. Opening a pass is not such a reset. A compile whose envelope failed outright is answered the same way: the pass retains that verdict for its remaining modules instead of repeating the identical failing compile once per module, and the next pass attempts it again. A host with no pass boundary keeps evicting a failed compile on every delivery, so a transient toolchain failure never becomes permanent for a long-lived worker. A failed compile whose project changed while it ran is compiled again, as a success whose proof was lost already is, because its verdict describes a state already gone. A host that records its dependencies when the transform returns, as Turbopack does, would otherwise keep showing the failure after the repair. One-shot calls without a cache retain their single compile. A whole-project compile never blocks the host’s event loop: the adapter runs it, plugin loading included, on a worker thread, so a dev server keeps answering other requests and a build keeps running its own work meanwhile.

Closing a webpack or Rspack compiler releases its bridge at the compiler’s shutdown hook. Its generation holds no watcher, and it is shared by every compiler in the process with the same options, because webpack creates the adapter once per compiler. It is kept for two seconds after the last compiler shuts down, so the next compiler proves it and reuses it instead of compiling the program again. That is how next build --webpack runs its server, edge, and client compilers, one after another. A non-watching vite build keeps its generation the same way from one environment’s build to the next, so a client and SSR build compile the project once. A generation that no session takes up within the grace is released. esbuild disposes after a one-shot build or after the last overlapping build context closes; an older delayed disposal cannot clear a replacement build that has already reached onStart. These terminal boundaries release generation-owned filesystem trackers without discarding the generation on each rebuild.

A compile that succeeded but has no output for one requested file is a fact about that file rather than about the generation, so the generation is left alone and the module is returned to the host untransformed, reported once per file per pass with the file and the tsconfig it is missing from. That is one answer shared by every adapter and by @ttsc/metro.

A failed compile registers the project-walk inputs, retained external inputs including transformed sources, graph members, plugin dependencies, and host inputs, and files named by its structured or standard TypeScript text diagnostics, so a watching session whose first compile failed still has a channel through which an internal or external fix arrives. These failure registrations make no claim about current input state; the adapter probes or watches each path for the repair. Every message the adapter surfaces is plain text, since what it returns becomes a bundler’s error in an overlay or a CI annotation rather than something a terminal renders.

A generation’s non-error diagnostics belong to the compile rather than to a delivery, so they are surfaced once per pass rather than once per delivered module, and a later pass over a retained generation surfaces them again.

Bun runtime setup defines one process-scoped loading session. A dev server started without a watcher takes the pass lifecycle instead of persistent validation: server.watch: null leaves the session no channel through which a file change could ever reach it, so what per-delivery validation buys there is incoherence rather than freshness, since modules delivered before an edit and after it would come from two different compilations of one program. Each module’s first delivery in such a session is therefore settled against the generation the session started from, exactly as under a build, while a module the session already delivered keeps revalidating on its next request.

This section is about the transform cache (which files a rebuild depends on), not the source-plugin binary cache (the compiled Go plugin ttsc builds on first use). They are independent: persisting a bundler cache such as Next.js .next/cache does not carry the plugin binary across builds, and a fresh CI or container build recompiles the plugin (the ttsc: building source plugin ... line) even with a warm bundler cache. To keep that first-build compile from recurring on every build, persist the binary cache as described in Build cache. In a monorepo, run ttsc prepare from the same project directory the bundler builds, so the warmed binary matches the cache key the bundler build looks up.

Transform source outputs outside the project walk are kept in that external snapshot too. A non-declaration output is reusable only when the graph carries its compiler-time content and physical-identity proof; a post-compile disk read cannot prove which bytes produced the output. Its source hash then lets sibling module requests validate the same generation without adding arbitrary output keys to the project-file universe.

CLI or bundler?

Whichever tool owns the build runs the pass. A plain Node library builds with npx ttsc. A frontend behind Vite or webpack builds through @ttsc/unplugin. A monorepo with both uses both, one per package. The plugin pass is identical everywhere, and diagnostics show up wherever the bundler surfaces them.
